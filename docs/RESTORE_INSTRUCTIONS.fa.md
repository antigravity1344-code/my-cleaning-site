# دستورالعمل پشتیبان‌گیری و بازیابی

مرجع: `docs/OPERATIONAL-PLAN.md`، بخش ۹ (پشتیبان‌گیری و بازیابی) و بخش ۱۰، آزمون ۹.

## ۱. پیش‌نیاز یک‌بار: کلید رمزگذاری

پشتیبان‌ها با AES-256-GCM رمزگذاری می‌شوند. یک‌بار کلید بسازید و در محل امن (مدیر رمز سازمان، نه در گیت) نگه دارید:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

مقدار خروجی (۶۴ نویسهٔ hex) را به‌صورت متغیر محیطی `BACKUP_ENCRYPTION_KEY` در محیط اجرای سرور (نه در فایل داخل مخزن) تنظیم کنید. **این کلید را گم نکنید** — بدون آن هیچ پشتیبانی رمزگشایی نمی‌شود.

## ۲. گرفتن پشتیبان

```bash
BACKUP_ENCRYPTION_KEY=<کلید ۶۴نویسه‌ای> npm run backup
```

متغیرهای محیطی اختیاری:
- `SITE_DB_PATH` — مسیر پایگاه دادهٔ زنده (پیش‌فرض `server/data/site.sqlite`)
- `BACKUP_DIR` — مسیر ذخیرهٔ پشتیبان‌ها (پیش‌فرض `server/backups`؛ **در استقرار واقعی باید به ذخیره‌سازی واقعاً جدا از همین سرور اشاره کند** — یک دیسک/سرویس دیگر، طبق سند عملیاتی)
- `BACKUP_KEEP` — تعداد نسخهٔ نگه‌داشته‌شده (پیش‌فرض ۳۰)

این دستور یک عکس لحظه‌ای سازگار از پایگاه داده می‌گیرد (حتی اگر سرور در حال نوشتن باشد)، رمزگذاری می‌کند، در `BACKUP_DIR` ذخیره می‌کند و نسخه‌های قدیمی‌تر از آخرین ۳۰ تا را حذف می‌کند.

**اجرای روزانهٔ خودکار:** این اسکریپت را با `cron` (یا زمان‌بند معادل محیط استقرار) هر روز یک‌بار صدا بزنید، مثلاً:

```cron
0 3 * * * BACKUP_ENCRYPTION_KEY=<کلید> cd /path/to/paksho-site && npm run backup >> /var/log/paksho-backup.log 2>&1
```

## ۳. بازیابی (روی محیط تمیز)

طبق سند عملیاتی، بازیابی باید **پیش از راه‌اندازی** و سپس **ماهانه** روی یک محیط تمیز (نه سرور زنده) آزموده شود.

1. مخزن را در یک پوشهٔ جدا و خالی کلون/کپی کنید (یا از یک کانتینر/VM تمیز استفاده کنید). **هرگز مستقیم روی `server/data/site.sqlite` سرور زنده بازیابی نکنید.**
2. فایل پشتیبان موردنظر را از محل نگه‌داری (خارج از سرور اصلی) به همان محیط تمیز منتقل کنید.
3. بازیابی را اجرا کنید (مسیر خروجی باید **تازه** باشد؛ اسکریپت روی فایل موجود رونویسی نمی‌کند):

   ```bash
   BACKUP_ENCRYPTION_KEY=<همان کلید مرحلهٔ ۱> npm run restore -- --file /path/to/site-backup-2026-11-09T03-00-00-000Z.sqlite.enc --out ./restored-check/site.sqlite
   ```

4. اسکریپت خودش `PRAGMA integrity_check` را روی فایل بازیابی‌شده اجرا می‌کند و در صورت خرابی، خطای صریح می‌دهد (نه موفقیت کاذب).
5. برای بررسی کامل بودن داده، سرور آزمایشی را با همین فایل بازیابی‌شده بالا بیاورید و از پنل مدیر داده‌ها را ببینید:

   ```bash
   SITE_DB_PATH=./restored-check/site.sqlite PORT=4001 npm run server
   ```

   سپس در پنل مدیر (مسیر `/admin`) وارد شوید و فهرست سفارش‌ها را با انتظار خودتان (آخرین سفارش‌های پیش از زمان پشتیبان) مقایسه کنید.
6. نتیجهٔ هر آزمون بازیابی (تاریخ، فایل پشتیبان استفاده‌شده، موفق/ناموفق، مشاهدات) را در همین پوشهٔ `docs/` یا در سیستم ثبت تیم یادداشت کنید تا سابقهٔ آزمون ماهانه حفظ شود.

## ۴. اگر بازیابی شکست خورد

- پیام `رمزگشایی ناموفق بود` → کلید اشتباه است یا فایل پشتیبان ناقص/دستکاری‌شده منتقل شده (مثلاً کپی نیمه‌کاره). فایل را دوباره از محل نگه‌داری کپی کنید.
- پیام `بررسی یکپارچگی پایگاه دادهٔ بازیابی‌شده ناموفق بود` → خودِ عکس لحظه‌ای هنگام پشتیبان‌گیری خراب شده؛ نسخهٔ قبلی‌تر را امتحان کنید و موضوع را به‌عنوان مشکل P1 گزارش کنید (سند عملیاتی، سیاست دروازهٔ پذیرش ایراد).
- مسیر خروجی را همیشه تازه نگه دارید؛ اگر اسکریپت دربارهٔ «مسیر خروجی از قبل وجود دارد» خطا داد، مسیر دیگری انتخاب کنید یا فایل قبلی را عمداً حذف کنید (هرگز به‌طور خودکار رونویسی نمی‌شود).

## سابقهٔ آزمون‌های بازیابی

| تاریخ | فایل پشتیبان/شرایط | محیط | نتیجه |
|---|---|---|---|
| ۹ نوامبر ۲۰۲۶ | سرور زنده‌نما با ۲ سفارش واقعی ثبت‌شده از مسیر عمومی `POST /api/orders`؛ پشتیبان با `npm run backup` گرفته شد | یک `git clone` کاملاً تازه از مخزن (بدون `node_modules`، بدون `server/data`) در پوشه‌ای جدا؛ فایل پشتیبان به‌صورت دستی به آن منتقل شد تا انتقال «بیرون از سرور اصلی» شبیه‌سازی شود | موفق — `npm run restore` رونویسی را رد نکرد چون مسیر خروجی تازه بود، `PRAGMA integrity_check` سبز بود، و هر دو سفارش (کد پیگیری، نام، آدرس، مبلغ، ساعت، وضعیت) دقیقاً با مقادیر اصلی مطابقت داشتند. نکتهٔ مفید: اسکریپت `restore.js` فقط به ماژول‌های درون‌ساختهٔ Node نیاز دارد، پس روی محیط تمیز حتی بدون `npm install` هم اجرا می‌شود. |

## مهاجرت‌های پایگاه داده

مهاجرت‌های `server/db.js` نسخه‌دار و idempotent هستند (`CREATE TABLE IF NOT EXISTS`) و روی هر پایگاه دادهٔ بازیابی‌شده‌ای هم به‌صورت محلی دوباره اجرا می‌شوند (`openDatabase` در شروع هر بار اجرا)، بدون نیاز به ابزار مهاجرت جداگانه.
